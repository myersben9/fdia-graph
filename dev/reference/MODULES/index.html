    Modules¶

    What every folder of the repository holds, then what every Python file does, in one line: the first paragraph of its docstring. Generated by tools/layout.py; edit the docstring (or REPO and DOCS in the tool), not this page. A toolkit's section names each file by its module under the toolkit's package: dataset.base is src/fdia_graph/dataset/base.py, se.base is analysis/src/fdia_analysis/se/base.py.

    The repository¶

    folder what it holds
    src/ the generation toolkit, the package fdia_graph (the distribution fdia-graph): generating a timeline and loading it
    analysis/ the analysis toolkit, the package fdia_analysis (the distribution fdia-analysis, which depends on fdia-graph): state estimation, localization, federated training, trust selection and the results store's code, with its own pyproject.toml, src/ and tests/
    tests/ the generation toolkit's test suite, and the helpers both suites share (their shared fixtures are in the root conftest.py)
    examples/ scripts a user copies: the quickstart, the training examples, the New York extension points
    results/ the results store: data only (one CSV per experiment and runs.csv), with the queries the docs read it through
    pipelines/ the builds of released data: the New York pool and timeline, and the MATLAB reference they are checked against
    tools/ repository tooling only: the gates, the generated docs, pull requests and releases
    docs/ the documentation, one folder per kind of page
    docs/getting-started/ tutorials: a first run, start to finish
    docs/guides/ how to do one task
    docs/concepts/ explanations: how a part is built and why
    docs/analysis/ one page per study with its figures: what was measured, on what, and the result
    docs/reference/ facts to look up: the file map, the data dictionary, the glossary, the formulas, the references
    docs/figures/ the images pages share, each with its data or its diagram source
    .github/ the CI workflows and the dependency updates

    The generation toolkit, fdia_graph¶

    file what it does
    fdia_graph fdia-graph — load & generate ML-only dangerous FDIA localization datasets (realistic measurement graphs).
    _lazy Public names that load on first use, for the nygrid packages and fdia_graph.generation.
    dataset FdiaGraph: a PyTorch-ready dataset over one HDF5 file, a timeline (one row per frame in time order, kind="timeline").
    dataset.base The loader's shared state and the constants its concerns read.
    dataset.clients The timeline as federated clients: each utility sees only its own meters, buses and labels.
    dataset.export A whole split at once: summary, and the arrays/tensors/frames of every kept record.
    dataset.graph The static graph of a shard: connectivity and the per-branch and per-bus physics, as tensors.
    dataset.physics The admittance matrices built from the static graph, and the clean power flow on every branch derived from the clean state through them.
    dataset.records One record at a time: unit conversion, __getitem__ in dict/PyG form, collate, and a ready DataLoader.
    dataset.sequence The timeline as sequences: sliding windows over a time-ordered view, and the episode table.
    download Fetch built-in shards from the GitHub Release and cache them under ~/.cache/fdia_graph.
    engine The generation engine — the math/physics/theory half of the SDK, behind fg.generate().
    engine.attacks Every attack the generator builds, behind one mixin: AttackMixin, mixed into FdiaGenerator.
    engine.attacks.area The attacker's area: the subnetwork a stealthy attack re-solves, and the boundary it holds true.
    engine.attacks.attacker The attacker: the local subnetwork it re-solves, the false state a pretended load implies, and the bounds the grid's own behaviour puts on a pretended change (natural_steps, generator_ramps, generator_band, generator_q_capability).
    engine.attacks.episodes What one episode attacks: its design, drawn at onset by the family's designer.
    engine.attacks.false_state The local false state of a stealthy attack: the attacker's area re-solved under false loads with the boundary held true, checked against the operating limits, and the attack vector it writes.
    engine.attacks.family What one attack occupies on the timeline, and the interface its two families share.
    engine.attacks.interface Am, the overload attack on a NYISO interface (N48, N49, ours): over a window of scans the reported flow across an interface rises to its limit, each scan the reading of one AC false state from OpfFdia's local OPF under every one of its bounds, so the operator's residual test stays quiet.
    engine.attacks.minimize The cheapest support of an attack window [WU26 eq. 12].
    engine.attacks.opf The attacker's false states from a local AC optimal power flow (N35): the support search and the per-scan OPF every OPF attack shares. OpfFdia is their base class; a subclass adds the goal and design (interface.InterfaceFdia, the one the release builds).
    engine.attacks.overload Am, the multi-snapshot overload attack of [WU26]: the reported flows of its target branches (two by default, as the paper's case studies overload two lines at once, or one; OverloadSettings.n_lines) driven to their ratings over the window, with the fewest devices tampered.
    engine.attacks.ramp At, the slow ramp: a false load that rises a little each frame, every step below the natural five-minute load swing, so no single snapshot looks anomalous while the total drifts the state away.
    engine.attacks.rref [WU26]'s own construction of the attack's support: row reduction of the transposed attack-area Jacobian with column exchanges.
    engine.attacks.stealthy The stealthy ramp At: one scan at a time, a local false state added to the true scan.
    engine.base Shared state contract for FdiaGenerator's mixins — attribute + cross-method annotations only.
    engine.core Dataset generation engine (attack simulation + realistic measurement emission).
    engine.measurement Measurement emission: turn a grid state into meter readings (the measurement function h(x)).
    engine.pandapower_types The pandapower objects the engine reads, as types.
    engine.physics A scan's load and generation, read from its stored state.
    engine.records One scan of the timeline writer: a benign scan, or an attacked At scan built by engine.attacks.
    engine.sensing The meters: what each client measures, and how wrong each meter is.
    engine.sensing.measure The measurement function: the meter readings a grid state gives, and their derivatives.
    engine.sensing.meters The meter plan: every meter on the New York buses as one row of a table, with its owner and accuracy class.
    engine.sensing.noise Meter noise: the accuracy class of each meter split into a constant bias and a per-scan jitter.
    engine.solvers The optimization solver every nygrid OPF runs on, found and checked in one place.
    errors Every error the package raises on purpose, in one place.
    formulas The mathematics of the generation toolkit as named, pure functions: numpy in, numpy out, no files, no dataset objects, no torch. Each function carries its equation and a source key from docs/reference/REFERENCES.md; docs/reference/FORMULAS.md is the catalogue. The formulas of estimation, localization, federated training and trust selection are the analysis toolkit's (fdia_analysis.formulas).
    formulas.attacks Attack shapes defined by the dataset [DAT26] that are pure functions of their parameters.
    formulas.network The AC network model: branch admittances, bus injections and branch flows [AE04, ch. 2], [MP19].
    formulas.noise The meter error model: accuracy-class standard deviations split into a constant per-meter bias and a per-scan jitter [ASP14], our split.
    formulas.temporal The temporal features of a scan [FED26]: the one-step injection change and its z-score against the bus's typical recent change, and the recent-change scale itself.
    formulas.trust Row reduction for stealthy attacks under trusted meters [WU26]: the reduced row echelon form of a matrix, and the sparsest rows of a row space, which the attack generator searches for an attack vector the trusted meters leave open.
    generation generate(system, name, **knobs) — build a custom dataset and register it as name.
    generation.design The design stage of a timeline: the overload Am episodes of a split, designed before it is walked.
    generation.emit The emit stage of a timeline: every frame in time order, benign or under its episode's design.
    generation.ieee An IEEE case as the source of a timeline: its pool of operating points and its steps of the driver.
    generation.nygrid The New York system: NYgrid's NPCC-140 case made solvable in AC, its reduced network, the 2019 loads by bus, the hourly dispatch and the five-minute pool of AC operating states, and the timeline written from them.
    generation.nygrid.case The grid as one frozen record of arrays, read from a MATPOWER case file.
    generation.nygrid.config Build settings and the one place random generators are made.
    generation.nygrid.dispatch Hourly unit dispatch, NYgrid's allocation of the NYISO fuel mix to the fixed unit list.
    generation.nygrid.fixes Two variants of a case, applied when one is asked for: the external areas held at the base load, and NYgrid's HVDC links in place of the AC branch 81-125. The changes every build has (zone J's split, the 765 kV line) are in the case file itself (case.py reads it).
    generation.nygrid.inputs Historical inputs: NYgrid's hourly 2019 tables and NYISO's 5-minute zonal load, and fetch_inputs, which downloads everything the build reads at its pinned version.
    generation.nygrid.interfaces NYISO's internal transmission interfaces on the reduced case, with their real 2019 hourly limits and flows.
    generation.nygrid.io The pool file of the build, HDF5. A timeline is written by the writer every grid uses (fdia_graph.generation.write) and read through fdia_graph.dataset.
    generation.nygrid.load_sources Where the bottom-up load profiles come from ([LI21]), each downloaded once into a cache: the NREL ResStock and ComStock county profiles, each utility's EIA-861 sector sales, the census county centroids and the IAC industrial plants, with the clock rules the plants run on. LoadModel (loads.py) builds the bus profiles from these.
    generation.nygrid.loads Per-bus load profiles by the bottom-up method of [LI21], scaled to the real zone load.
    generation.nygrid.network Admittances of a Case, built once, and the AC quantities they give for any state, from the SDK's network formulas (formulas.network).
    generation.nygrid.ownership Federated clients: each NY bus belongs to the electric utility whose service territory holds it.
    generation.nygrid.pool The pool: one AC operating state per 5-minute frame, from a ramp-constrained real-time dispatch (N32).
    generation.nygrid.solver AC solutions of a Case: the hourly projection (an AC-OPF in Pyomo, solved by Ipopt) and the power flows between hours (pandapower).
    generation.nygrid.source The New York grid as the source of a timeline: the year of pool states and its steps of the one path.
    generation.nygrid.tables The CSV tables of the inputs, read whole and closed: the NYgrid checkout's bus, unit and renewable tables and the bus locations. One reader, so no input file is left open (each was a ResourceWarning before).
    generation.plan The plan stage of a timeline: where its splits are cut and where each split's episodes go.
    generation.source The system a timeline is generated on, and the one path that generates it.
    generation.write The write stage of a timeline: its datasets, columns, episodes and attributes in the HDF5 file.
    models Every data model of the generation toolkit in one place.
    models.assets How files are found: where a dataset comes from, where its bytes are fetched from, and one line of the N-1 candidate list.
    models.base Bundle: a typed record that still IS the dict it used to be.
    models.choices Every argument that takes one value from a fixed set, in one place.
    models.config The settings every consumer accepts, one model each, checked when built (models.validation).
    models.data What a user gets back: one record, a batch, a whole split, a summary, the episode table, and the per-record truth an estimator is scored against. Each is a Bundle, so it is still the dict it always was.
    models.errors The named errors of conditions only the data reveals, beside ConfigError so a model can raise one (Validated.error), and the one error of an environment that cannot run a step (SolverUnavailable). fdia_graph.errors re-exports every one.
    models.fields The field groups the data bundles share.
    models.frames What the generator passes around per scan: a measurement scan, the emitted frame with its labels, the run's attack knobs, the design of an At ramp and of an Am overload episode, and what the fewest-tamper search returns.
    models.grid The static description of a system: the per-branch pi model and the admittance matrices built from it, which meters exist, the constant meter bias, and the N-1 contingency a generator was built with. Nothing here changes from one scan to the next.
    models.inputs What the formulas and the parsers accept, one model each, checked when built (models.validation).
    models.plan The records of a timeline's plan and design stages: a placed episode (Slot), a split and its frames (SplitSpan), an episode not yet written (Pending) or with its design (Designed), what is placed (Schedule) and what the placement asked for and got (Placement), and what a design worker rebuilds its generator from (GeneratorSpec).
    models.validation The one place inputs are checked (CONTRIBUTING.md, "an input is checked in one place").
    profiles Load-profile ingestion + operating-state generation — the FRONT of the pipeline.
    ratings Branch thermal ratings for the overload attack of [WU26] (eqs. 24-25), stored with the package.
    registry Dataset registry: built-in (downloadable) datasets + locally generated ones.
    schema The file protocol: every group, dataset and attribute name an fdia-graph HDF5 file carries, defined once. The writer (timeline, generation), the readers (dataset) and the tools agree through these names and nowhere else; tools/readability.py refuses a path-shaped literal ("data/...", "graph/...") in any other module. Field names (node_x, clean, ...) are the public vocabulary of a record and stay as words in the code; FIELD_PATH maps them here.
    timeline One continuous attacked timeline per system, written as one HDF5 file.

    The analysis toolkit, fdia_analysis¶

    file what it does
    fdia_analysis fdia-analysis: what is measured on an fdia-graph timeline: state estimation, attack localization, federated training, trusted-meter selection, and the store the measured results are kept in.
    federated Federated training over K clients (utilities) that never pool their records [FED26].
    federated.aggregate Averaging torch state dicts across clients with formulas.federated.fedavg [MCM17].
    federated.localizer Federated per-bus localizers: the paper's BusMLP and BusCNN trained by FedAvg over K clients [MCM17], [FED26], with records never leaving a client.
    federated.partition The split of a system's buses into K clients (utilities) for federated training [FED26].
    federated.se Federated fitting of the state estimator's learned part [EST26], [FED26].
    formulas The mathematics of the analysis toolkit as named, pure functions: numpy in, numpy out, no files, no dataset objects, no torch. Each function carries its equation and a source key from docs/reference/REFERENCES.md; docs/reference/FORMULAS.md is the catalogue. The network model, the meter noise and the attack shapes are the generation toolkit's (fdia_graph.formulas).
    formulas.estimation Weighted least squares state estimation and its robust variants, one function per equation [SCH70], [HAN75], [HUB64], [EST26].
    formulas.federated Statistics that combine across federated clients without moving their records [FED26].
    formulas.linalg Numerical linear algebra the estimators lean on: a guarded inverse of a normal matrix, its condition number without an eigen-decomposition, and per-record normal matrices in sub-batches.
    formulas.measurement The estimator's AC measurement function h(x) and its closed-form Jacobian [AE04, ch. 2], [MP19], assembled from the network model the generator and the loader use (fdia_graph.formulas.network: bus_injections, branch_flows). The estimator's torch twin (se.base.SEBase._h_t) is kept for callers that differentiate through it; analysis/tests/test_formulas.py pins it to the functions here.
    formulas.metrics Per-bus localization metrics from confusion counts, so they can be summed across clients or thresholds before any ratio is taken [KEC25].
    formulas.projection Projections through the measurement Jacobian: the explained and unexplained parts of a measurement change, leverage, the weak directions, and the meter-to-bus aggregation of the Jacobian-informed features [JAC26], [HAN75].
    formulas.trust Trusted-meter selection against stealthy attacks [WU26]: the attack subspace a secured set leaves open, the cost of the cheapest attack in it, and the greedy selection that closes it.
    localization Per-bus FDIA localization on fdia-graph datasets, sklearn style.
    localization.base Per-bus FDIA localization on fdia-graph datasets — the shared machinery behind every method class.
    localization.learned Learned per-bus localizers: the graph-free encoders that gave the best localization numbers in the federated localization paper, on that paper's 14-dim per-bus feature vector.
    localization.methods The localizer method classes. Each changes exactly one thing about LocalizerBase — the per-bus score — so a difference between two arms is a difference between detection signals, not between calibration or metrics code.
    models Every data model of the analysis toolkit in one place: the ones only the estimators, the localizers, the federated trainers, the trust selectors and the results store use. A model the generation toolkit also uses is in fdia_graph.models, and is imported from there.
    models.choices The fixed sets the analysis settings choose from, beside fdia_graph.models.choices (its Choice is their base): a member is its string value, and a settings model declares a field's set as Annotated[str, OneOf(Features)].
    models.config The settings the estimators, the localizers, the trust selectors and the federated trainers accept, one model each, checked when built by the validation engine of fdia_graph.models.validation.
    models.data What the analysis packages hand back that is neither a score table nor a setting: the truth an estimator is scored against.
    models.federated What the federated layer passes around: how the buses split into clients.
    models.grid The pseudo-measurement records of the estimator's PMU current channels [WU26 eq. 3]: where a pseudo voltage phasor can be placed, and the phasors with their propagated noise.
    models.inputs What the analysis formulas accept, one model each, checked when built by the validation engine of fdia_graph.models.validation.
    models.results The models of a results table: the metric registry, a Record (one measured value with the keys that say what it is) and a Provenance (which run made it), plus the parsers that read loose input (a nested score report, a filter value, a run's settings) by its type. Every check lives here, per the validation rule, so a store never holds an unknown metric, a non-finite value or a malformed key; fdia_analysis.results builds these models and never checks its input itself.
    models.scores The result tables: an estimator's error pair per record class, a localizer's metric rows per class, and the Jacobian feature outputs. Each is a Bundle, indexable by family name as before.
    models.training What the learned localizers pass between their fitting pieces (a centralized fit and a federated client share them).
    results Measured results as data: typed records with their provenance, one tidy store, and the renderers that put the numbers into docs and figures, so no measured number is typed by hand.
    results.docs Measured numbers in markdown come from the store, never from a keyboard.
    results.render Turning records into what a reader sees: a formatted cell, a markdown table, a pivot of records by two keys, and the CSV sidecar a figure is drawn from. Nothing here measures or stores anything.
    results.run How a harness records what it measured: open a Run, add values, and the run writes them to the store with its provenance when it closes.
    results.store The results store: one tidy CSV per experiment plus one table of runs, in a folder kept in git.
    se State estimation on fdia-graph datasets, sklearn style.
    se.base State estimation on fdia-graph datasets — the shared machinery behind every method class.
    se.detect Detection: when a detector alarms, as a building block.
    se.detect.rules When a detector alarms: the rule that turns a statistic per scan into a first alarm.
    se.jacobian Jacobian-informed features (Abdulin & Narimani): the measurement Jacobian as a physics transform of the scan-to-scan measurement change, not as raw model input.
    se.methods The estimator method classes. Each changes exactly one thing about SEBase, so a difference between two arms is a difference between estimators rather than between implementations.
    trust Which meters to trust so that stealthy attacks stop being stealthy [WU26], sklearn style.
    trust.base The shared machinery of the trusted-meter selectors: the measurement Jacobian at the benign mean (from a WLS estimator of fdia_analysis.se), the attack-cost kernel, and the scoring that pins the secured meters and asks the residual test whether the attack shows.
    trust.meter_dqn The trusted-meter selection as a Markov decision process solved by a deep Q-network (the learned selection of [WU26]).
    trust.secured A copy of a timeline with a set of meters secured: the attacker locked out of them, so on every frame their observed reading is the benign one, and the stored temporal features recomputed from the pinned observed frames (generation.write.write_temporal_layers). The estimators and the localizers then read the copy like any timeline, which is how a trusted-meter selection is measured on state estimation and localization rather than on the residual test alone (TrustSelector.score). The copy is rewritten in blocks of frames, so a 72,000-frame timeline of any ladder system fits in bounded memory.

    Tools¶

    file what it does
    tools/bench.py Time the estimators and the generator on the tiny timeline, and store the timings as a run of the bench experiment in the results store (results/bench.csv), where docs/reference/BENCHMARKS.md renders them from (a results block).
    tools/class_diagrams.py Write the class and module diagrams of the two toolkits (fdia_graph and fdia_analysis) from their source, as Mermaid sources under docs/figures/diagrams/, so the pictures in docs/reference/CLASS_MAP.md never drift from the code.
    tools/layout.py The repository's layout rules, and the file map they keep current (docs/reference/MODULES.md).
    tools/models_doc.py Render the public data models into docs/reference/DATA_DICTIONARY.md.
    tools/pr.py Pull requests from the command line, without the gh CLI (CONTRIBUTING.md, "The pull request").
    tools/prereview.py Every check a pull request must pass, for both toolkits of the repository (fdia_graph and fdia_analysis, sources.PACKAGES), run locally in one command before the review is requested (CONTRIBUTING.md, "The pull request").
    tools/readability.py Readability measures for the two packages (fdia_graph and fdia_analysis, sources.PACKAGES), the limits below (LIMITS), and the file-protocol rule: a dataset path ("data/...", "graph/...", any group of schema.Group) or a group name used as one (f.create_group("data"), f["attack"], "episodes" in f) may be spelled only in src/fdia_graph/schema.py; every other module goes through schema. And the validation rule (CONTRIBUTING.md, "an input is checked in one place"): raise ValueError / raise TypeError and isinstance(...) only inside a models package (fdia_graph.models, fdia_analysis.models), where the one engine checks every input and the parser models read loose input by its type; everywhere else an input is checked or parsed by building its model, and a condition only the data reveals raises a named error from errors. And the typing rule: an annotation says Any only where ANY_ALLOWED lists it with the reason the value can be anything; every other annotation carries its real type.
    tools/release.py Cut a package release after the version-bump PR has merged (CONTRIBUTING.md, "Releasing").
    tools/render_mermaid.py Render a Mermaid source file to a standalone SVG and a PNG next to it. Every diagram in the docs is such a rendered image, because the README is also the PyPI page and the docs are read in the GitHub mobile app, and neither renders a Mermaid block.
    tools/results_docs.py Fill and check the results blocks of the docs from the results store (results/).
    tools/site_index.py Stage the three root pages of the repository for the docs site: README.md becomes docs/index.md, CONTRIBUTING.md docs/contributing.md and CHANGELOG.md docs/changelog.md. The README is the single source for the landing page; its links carry a docs/ prefix that is wrong once the file lives inside docs_dir, so the prefix is stripped on copy, and links between the three root pages are rewritten to their staged names. Runs in the Vercel build (vercel.json) and in the versioned deploy (.github/workflows/docs.yml); the three staged files are generated output and stay untracked.
    tools/sources.py Where the repository's two toolkits live, said once for every tool: the generation toolkit fdia_graph and the analysis toolkit fdia_analysis, each a package under its own source root.
    tools/upload_assets.py Publish data-release assets to a GitHub release (CONTRIBUTING.md, "Releasing", data releases).

    The generation toolkit's tests¶

    file what it does
    tests/case_studies.py [WU26]'s case studies as test inputs: the lines each scenario overloads, its PMU buses and the attacker's area, in MATPOWER bus numbers, and their positions in a generator's grid.
    tests/digests.py Whole-file digests of a generated HDF5 file: the proof that a refactor did not move a number.
    tests/helpers.py The plain helpers the two test trees share (tests/ and analysis/tests/): where the checkout's parts are, the tiny timeline's recipe, the old releases' files, and the checks both toolkits hold their own package to. The fixtures are in the repository root's conftest.py.
    tests/nygrid/conftest.py The synthetic New York grid the timeline tests share: the packaged case file with made-up clients, eight weeks of hourly made-up states and two families that write a bias on one meter, so a timeline is generated with no NYgrid data and no solver.
    tests/nygrid/inputs.py The inputs of the nygrid tests in one place, and which tests each one lets run.
    tests/nygrid/test_attacks.py The New York attacker on the real grid: its area and edge rules, the false state of a pretended load, the ramp built on it (within the natural load swing, quiet to the residual test), and the bounds it reads from the pool.
    tests/nygrid/test_case_file.py Case.from_matpower on a three-bus case file written here: what it reads and what it refuses. Needs no input data.
    tests/nygrid/test_configs.py Settings are passed in, never patched onto shared objects: a widened case and an overshoot variant are copies, and the originals stay as they were (no data needed).
    tests/nygrid/test_dataset.py A New York timeline read back (dataset.clients): the file holds what the source stored, in the layout of fdia_graph.schema; the meter table and the flat reading vector come back from its layers exactly; each client sees only its own meters, buses and labels; the operator and split views select the right frames; and the static graph gives the case's admittance matrix. On the synthetic grid of conftest.py: no data, no solver.
    tests/nygrid/test_examples.py The extension examples of docs/guides/extending_new_york.md run as published, so the guide never shows code that broke (no data needed).
    tests/nygrid/test_golden.py Golden snapshots of nygrid's outputs on fixed inputs, the safety net of the readability refactor.
    tests/nygrid/test_grid.py The New York grid's case file: what it holds, its exact round trip through the MATPOWER reader and writer, the recipe that made it from NYgrid, the two case variants and the utility of each bus.
    tests/nygrid/test_misses.py Every design that finds no attack says why (a miss reason), so a timeline with few attacks can be read: nothing to attack, nothing feasible, or a solver that failed (no data needed).
    tests/nygrid/test_public.py The public surface of the New York code: every package's names resolve, reading a dataset stays light, and the names that became public keep their old spelling for one release (no data needed).
    tests/nygrid/test_release_source.py The release source's attacker sensitivities stay with the attacker: a timeline built with v_margin records the case's true voltage limits, while the attacker designs against the widened ones (N71). Needs the public inputs and the whole 2019 pool (inputs.py).
    tests/nygrid/test_scenario.py The hourly operating points against NYgrid's own MATLAB output: the inputs, the dispatch, the AC projection and the pool, and the bottom-up load profiles with their within-hour calibration.
    tests/nygrid/test_sensing.py The New York meter plan and its readings: the fewest PMUs on small graphs, the plan, the measurement Jacobian against finite differences, observability and the meter noise.
    tests/nygrid/test_solvers.py The checked Ipopt every nygrid OPF runs on: a solver that is missing, or found but unable to start, raises SolverUnavailable with the fix, instead of reading as an infeasible model downstream.
    tests/nygrid/test_stretches.py The New York source on a synthetic pool, with no NYgrid data and no solver: the frames written in stretches as the weekly splits are planned are the frames written in one pass, one source generates the same file twice, a single episode is the design of its (lagged) window on the true scans, and a failed run leaves no file.
    tests/nygrid/test_tables.py The input tables are read whole and closed: no ResourceWarning, a byte-order mark dropped (no data needed).

    tests/test_malformed_inputs.py A malformed setting or argument is a ConfigError, never a raw TypeError, KeyError, ValueError or IndexError from deeper in the code (docs/reference/REVIEW_CHECKLIST.md, item 4).
    tests/test_minimize.py The fewest-tamper support search [WU26 eq. 12]: exact against brute force on IEEE-14, a lower bound that never exceeds a cost, the two sigmas (the emitter's per-scan jitter, the meters' accuracy class the search counts against), and a continuous reweighted-l1 cross-check the search is never beaten by.

    tests/test_one_path.py The one path that generates a timeline (TimelineSource.generate), checked on the parts both grids share: how far the walk may run once a split is planned, where an episode fits in a split that lists its frames, the worker pool the designs run on, and what a run leaves on disk when it fails.
    tests/test_overload.py Am as the overload attack of [WU26]: the PGLib-OPF line ratings, the flow-goal false state, the eligible target branches, the fewest-tamper search on a flow goal, and new generation's families.
    tests/test_overload_case_studies.py [WU26]'s case studies on our overload attack: the paper's PMU placement, its two lines overloaded at once, the ratings 1.2 times each line's peak true flow over the window (the level at which our device counts matched the paper's in the S_max sensitivity study), and the D16 bounds. The paper states no line limits, so the ratings are ours and the comparison is of kind, not of value: the attack is feasible, reaches both ratings, tampers the paper's devices on IEEE-14, and its largest per-device change is of the paper's order (0.22 and 0.17 pu there).
    tests/test_package_equivalence.py Hand-written loops and formulas replaced by library calls or array operations: each test pins the replacement to the code it replaced (identical, or to tolerance where the arithmetic order changes), so the simplification cannot drift.
    tests/test_pmu_channels.py The hybrid meter model: angles at the PMU buses only, the PMU branch-current phasors [WU26 eqs. 19-20] emitted, stored, loaded and attacked, and the eq. (3) pseudo-measurements an estimator can derive from them. The v0.8.3 meter model stays the default and writes none of it.
    tests/test_profiles.py Load sources and operator feeds: each reads itself, no network needed.
    tests/test_public_bundles.py The public dual-access bundles (data models step 3): each is the dict it used to be, with the same keys in the same order, and its attribute view agrees with the dict view.

    tests/test_registry.py The registry's asset layout: one timeline per system and its HDF5 pool, from data release v0.8.0.
    tests/test_rref_attack.py [WU26]'s row-reduction attack (p. 655 and Sec. IV-D1 steps 1-5, after [YAN17]) as the overload attack's support method (OverloadSettings.support_method="rref"): the column-exchange reduction, the supports it pins on the paper's IEEE-14 scenarios, and that the attack it builds is feasible.
    tests/test_schema.py The file protocol lives in one module: the fixture file carries exactly the names it spells, and no other module spells a dataset path.
    tests/test_sdk.py Behavioral tests for the SDK surface: the contracts the docs promise, checked on a tiny timeline.
    tests/test_search_speed.py The fewest-tamper search's speed-ups change nothing it finds: exhaustive searches on fixed IEEE-14 windows return the answers the search returned before them (pinned), and each shortcut equals the computation it replaced (the cached boundary, the reused solve blocks, the attack vector over the support's branches only).
    tests/test_split_first.py Split-first generation: the timeline is cut into train, val and test before any episode is placed; each split gets the whole number of episodes closest to its attacked fraction, shared between the families by largest remainder and placed uniformly without overlap or cut; an episode with no feasible design moves to another onset of its split (an Am anywhere in it, a ramp later); and every frame's jitter comes from its own (seed, timestep) stream, so timelines that place different attacks carry the same benign frames.
    tests/test_timeline.py The one-file timeline writer: its layout, its episodes and the At and Am frames.
    tests/test_timeline_digests.py The generated IEEE timeline, whole: every dataset and attribute of the file against a stored digest.
    tests/test_toolkit_boundary.py The dependency between the two toolkits points one way: the analysis toolkit fdia_analysis builds on the generation toolkit fdia_graph, and fdia_graph never imports it. Checked in the source (no import, no module name in a lazy table) and by running: a fresh interpreter in which fdia_analysis is blocked (so the check is the same whether or not it is installed) loads every module of fdia_graph, generates a timeline and reads it back.
    tests/test_trust_formulas.py The row reduction the attack search and the trusted-meter kernel share (the kernel itself, the open attack subspace, its cost and the greedy selection, is checked in analysis/tests/test_trust_formulas.py).
    tests/test_trusted_pmus.py [WU26]'s trusted-PMU schedule as a constraint on the fewest-tamper search: a PMU trusted at slot s keeps its bus's /V/ and angle true at every snapshot t >= s (eqs. 26-32), its branch currents stay untrusted (eq. 27), and one support is held for the window.
    tests/test_validation.py The validation engine (models.validation): rules declared on fields, one message shape, and the public entry points that build their config models before any work.
    tests/test_versions.py The two toolkits are released together at one version: both pyproject.toml files and both __version__ values say the same number, and fdia-analysis requires exactly that fdia-graph (a released fdia-graph of another version may lack a name fdia_analysis imports). No data needed; tools/release.py refuses to tag a commit where this does not hold.

    Pipelines¶

    file what it does
    pipelines/newyork/build_single_episodes.py The single-episode files for studying one attack by hand: one Am on an interface per file, over the whole day it falls in (288 five-minute scans), nothing else attacked. Each file is a normal timeline (fdia_graph.dataset.clients.Dataset reads it): the scans with the attack, the same noisy scans without it, the true states and the labels. Each is generated by the path every timeline takes (TimelineSource.generate), over the release's grid with that one episode (SingleEpisodeSource).

    pipelines/newyork/run_pool.py Build the P5 pool for a time window as NYISO's real-time dispatch (N32, N39), in chunks run in parallel.
